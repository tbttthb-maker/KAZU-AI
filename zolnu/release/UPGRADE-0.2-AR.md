# ZOLNU 0.2 — الملفات الشخصية وحملة المؤسسين

هذه النسخة تضيف صور الحساب والغلاف، وخمسة أنماط إطار، وشارات الشركة والمؤسس، ولوحة حملات للشركة. ملف المصدر لا ينشئ حسابات عامة أو يفعّل حملة على خادم غير معد.

## حساب الشركة

البريد المحجوز للمالك: **tbttthb@gmail.com**. لا توجد كلمة مرور افتراضية ولا حساب مصادقة أنشأته هذه الملفات.

بعد إعداد Supabase وتشغيل المخطط والترقية، أنشئ حسابًا بهذا البريد من التطبيق، وأكد البريد من الرسالة التي ترسلها خدمة المصادقة، ثم سجّل الدخول. `claim_company_account()` يتحقق من بريد المستخدم المؤكد داخل `auth.users` ومن `auth.uid()` قبل منح صلاحية الشركة. لا يعتمد على الاسم الظاهر أو user_metadata أو مقارنة بريد داخل JavaScript.

اسم المستخدم `zolnu` محجوز ولا يستطيع مستخدم عادي أخذه. حساب الشركة يحمل شارة ذهبية مستقلة عن شارة المؤسسين. لا تدخل بريدك أو كلمة مرور Apple داخل ملفات الكود.

## حملة التوثيق

- انشر من حساب الشركة، وفعّل خيار «التوثيق الدائم للايكات لهذا المنشور»، أو اختر منشورك من مركز الشركة.
- اختر مدة 1 أو 24 أو 48 أو 72 ساعة. الافتراضي 48 ساعة. دالة السيرفر تسمح 1–720 ساعة.
- اللايك الجديد الذي يُسجّل خلال المدة يضيف سجلًا دائمًا في `verification_grants` بواسطة trigger في قاعدة البيانات. توقيت السيرفر هو المرجع.
- إزالة اللايك أو إيقاف الحملة أو انتهاء موعدها أو حذف منشور الحملة لا يزيل الشارة الممنوحة. لا يوجد حقل انتهاء للشارة. الديمومة للحساب نفسه، ولا تعيد بيانات حساب حُذف نهائيًا.
- لا تُمنح الشارة بأثر رجعي للايك سابق على بدء الحملة. إزالة اللايك وإضافته داخل فترة الحملة تُعد مشاركة جديدة.
- شارة المؤسس مكافأة حملة داخل التطبيق؛ وهي مختلفة بصريًا عن صلاحية حساب الشركة الرسمي.
- إطار المؤسس يُفتح لحامل الشارة. بقية الإطارات متاحة للجميع.

## ترقية الخادم

على قاعدة جديدة: نفّذ `supabase/schema.sql` ثم `supabase/migrations/002_company_profiles.sql`.
على قاعدة 0.1 موجودة: نفّذ الترقية `002_company_profiles.sql` فقط، مرة واحدة بعد أخذ نسخة مناسبة من بياناتك.
ملفات الترقية هنا لم تُنفّذ على خادم مستضاف خلال جلسة الإنشاء؛ اختبارات PostgreSQL المحلية تنفذ نفس SQL مع جداول مصادقة وتخزين بديلة للاختبار.

لا تمنح دور authenticated صلاحيات INSERT/UPDATE/DELETE على جداول company_accounts أو verification_grants أو verification_campaigns. أزرار الإدارة تستدعي دوال تتحقق من المستخدم على السيرفر.

## الصور والإطارات

الصور والغلاف بحد 3 MiB لكل ملف. على الهاتف تُنسخ وسائط التجربة لمجلد التطبيق، وفي المتصفح تُخزّن كبيانات محلية. الخادم المتصل يرفعها إلى bucket media العام في مسار صاحب الحساب. رابط الصورة والغلاف عام مثل بقية الوسائط؛ لا تعتبرهما خاصين.
الغلاف يعرض الصورة باقتصاص بصري يناسب المساحة، ويمكن تغييره من تعديل الملف الشخصي. الإطارات: بدون، أورورا، شمسي، نيون، المؤسس.

## بناء IPA لـSideloadly

الملف `.github/workflows/build-ipa.yml` يعرّف بناءً يدويًا على macOS من GitHub Actions. يستخدم `scripts/build-ipa.sh` لبناء تطبيق arm64 حقيقي عبر Xcode ثم يغلّفه في Payload/…app وIPA. لا يحوّل كود المصدر أو معاينة HTML إلى IPA بالاسم فقط.

للتشغيل في مستودع GitHub تملكه:

1. ضع محتويات المشروع في جذر المستودع، بما فيها `.github`، وفعّل Actions إذا لزم.
2. افتح Actions ثم **Build ZOLNU IPA for Sideloadly** ثم **Run workflow**.
3. انتظر نجاح البناء، ثم نزّل artifact **ZOLNU-Sideloadly-IPA**.
4. فك ضغط artifact وخذ `ZOLNU-Sideloadly.ipa` واسحبه إلى Sideloadly. الملف الناتج غير موقّع؛ Sideloadly يوقّعه بحساب Apple الذي تختاره على جهازك.

يمكن للـworkflow بناء وضع التجربة بدون مفتاح Apple أو شهادة مدفوعة أو أسرار خدمة. لتفعيل الخادم داخل البناء أضف أسرار Supabase العامة في إعدادات المستودع بالأسماء الموجودة في workflow. لا تضف service role.
قد تحتاج دقائق/رصيد Actions وفق خطة GitHub والمستودع؛ لم تبدأ أو تُدفع أي عملية بناء سحابية بهذه الملفات وحدها.

لبنائه على Mac تملكه:

```bash
npm ci
bash scripts/build-ipa.sh output
```

الحزمة غير الموقعة ليست إصدار App Store. لم يُتحقق من بناء Xcode أو تثبيت iPhone فعليًا حتى ينجح workflow ويُختبر الناتج. أي خطأ في أدوات Apple أو تبعيات iOS يظهر في build.log ويحتاج إصلاحًا قبل وجود IPA صالح.
